\section{Phase 1: Data Collection and Tokenizer Construction}
%=====================================================================

I have chosen Hindi as the higher-resource language: IndicCorpV2 gives it three data shards plus a Wikipedia dump, so manual collection could focus on \emph{variety} (encyclopedia and news) instead of just volume. Nepali had less to work with: IndicCorpV2 gives it only one file, and there is no Nepali Wikisource, so all manual data came from news APIs instead. This is a real constraint, not something set up on purpose. Both languages use the same Devanagari script, kept fixed so any gap found later is about resources, not alphabet.

Both corpora pass through the same 12-step pipeline: download, normalize, filter, dedupe, split, remove train/test overlap, train the tokenizer, then tokenize. No code under \texttt{shared/} may mention either language by name; a test enforces this automatically, since it is too easy to accidentally special-case one language while working fast.

Two choices are worth explaining. First, \emph{when} to remove train/test overlap: doing it before the split would let overlap-removal quietly decide which lines land in val/test, so I split first, locked val/test, and only then cleaned train against them. Second, which copy to keep when text appears twice: the manual copy always wins over IndicCorp (Hindi: Wikipedia, then news; Nepali: Onlinekhabar, then Khabarhub), a deliberate choice since the 20\% manual-data target is the harder one to hit.

Filter thresholds were judgment calls, not tuned values. The Devanagari-purity cutoff is 0.60 for Hindi but 0.70 for Nepali, lower because Hindi news mixes in more English, later confirmed at 6.00\% Latin content (\S\ref{sec:corpus-health}). Duplicate detection uses a fairly strict setting; the train/test overlap check uses a looser one, since catching every possible overlap there matters more than being precise, a missed one means real leakage into the test set.

Both models use a 12,000-word vocabulary, chosen at the point where bigger vocabularies stop paying off: 10K$\to$12K still gave a solid compression gain, 14K$\to$16K gave much less, for both languages. Past that point every extra word costs part of the fixed $\sim$25M-parameter budget. Using one shared size also means a later perplexity gap cannot be blamed on one model simply having a bigger vocabulary.

One pattern keeps showing up throughout this project: Nepali needs more tokens per word than Hindi (10.4\% more, on average). This comes from grammar, not bad data. Nepali sticks small grammatical pieces onto the end of a word with no space (so "Nepal" plus "of" becomes one word, \dn{नेपालको}), while Hindi keeps that piece separate. This is also why Nepali has more unique words than Hindi (6.80M vs.\ 3.96M): sticking pieces together creates more distinct word forms for the tokenizer to cover. Example: Hindi's \dn{भारत एक विशाल देश है।} splits into 6 whole-word tokens; the similarly short Nepali \dn{नेपाल एक सुन्दर हिमाली देश हो।} takes 7. Both tokenizers struggle equally on modern AI/ML terms absent from either corpus, e.g.\ "machine learning" breaking into 6--10 fragments.

\label{sec:corpus-health}Before trusting the above, I checked the corpus itself. Devanagari purity is 90\% or higher in every source, so the script filter works. Hindi's news carries 6.00\% Latin-script content, mostly English names mixed into sentences; Nepali's news is cleaner ($\geq$98.8\% Devanagari), likely a style difference rather than a quality one. The bigger finding is document length: news articles average 1,499--2,494 characters against IndicCorp's 218--286-character fragments, so one manual article is worth roughly 7--10 IndicCorp entries. That is why manual data reaches $\sim$18\% of tokens while being only 3--8\% of documents collected, and why every "manual fraction" number here is counted \textbf{by token}, not by document.

\section{Phase 2: Model, Pretraining, and Evaluation}
%=====================================================================

{\sloppy The model is a decoder-only Transformer built from basic building blocks, with no ready-made Transformer layer and no library like HuggingFace, since the point of this phase was to understand attention and masking directly rather than hide them behind a library.\par} It has 6 layers and 8 attention heads, about \textbf{25.3 million} parameters, identical for both languages so any later difference comes from data and language, not architecture. Causal masking (each token sees only earlier tokens) was checked directly: changing a future token and re-running confirms earlier predictions do not change.

I chose a wider, shallower model (6 layers) over a narrower, deeper one (12 layers) for two reasons: tying the input and output word-embeddings together frees up parameters better spent on width, and with $\sim$650M training tokens for a 25M-parameter model, there is already more than enough data, so extra depth would not help much. I also used a training-stability trick called pre-norm, since a crashed run on a cloud GPU means starting over from scratch, and a simple learned lookup table for positions rather than a fancier method, for easier debugging, at the cost of a 512-token limit this project never actually reaches.

Pretraining uses the AdamW optimizer, a warmup period, slow learning-rate decay, and mixed-precision training. Training runs for exactly one epoch, since both corpora already exceed what a model this size needs, so a second pass would mostly encourage memorization. The checkpoint-and-resume logic was tested to produce identical results whether training runs straight through or is stopped and resumed, since cloud sessions can be cut off without warning.

The most interesting finding here: which model looks "better" flips depending on how you measure it. On perplexity, Nepali looks 58.4\% worse (41.52 vs.\ 26.21). But perplexity is measured in each model's own tokenizer, and Nepali's tokenizer needs 10.4\% more tokens for the same text, so it is working with less real content per step, unrelated to how well it actually learned. Switching to bits-per-byte, a measure based on raw text bytes instead of tokens, the result flips: Nepali is actually 3.4\% \emph{better}. This holds on the test set too, and steadily from partway through training onward, not just at the end. The same idea shows up again, differently, in the Phase 3 results (\S\ref{sec:p3}).

To test generation, both models completed 500 held-out prompts at settings from safe (greedy) to more random (higher temperature), scored against the real continuation using each language's own subword pieces rather than whitespace words, since whitespace scoring would unfairly penalize Nepali's larger word inventory. BLEU turned out close to useless: a small model rarely matches a reference continuation word-for-word, so scores stayed low across the board, an honest limit of the metric, not a sign the models are bad. chrF, which gives partial credit for a correct stem with a different ending, was far more useful, since that near-miss is common in both languages' grammar, and was the only metric that reliably improved with more random sampling.

Repetition mattered more than any overlap score. Under greedy decoding, both models tend to get stuck repeating the same phrase (roughly 70--76\% of the time), something overlap metrics barely notice but a diversity metric catches clearly, dropping sharply once sampling gets more random. One real Hindi example: given a prompt about the rural economy, the model produced a grammatical, on-topic sentence but visibly repeated "for development" instead of finishing the thought. On attention, both models' heads split into nearby-focused and farther-focused groups; Nepali leans more toward nearby words overall, fitting the earlier finding that a Nepali word split into more pieces needs its next-piece clue close by.

\section{Phase 3: Reasoning Finetuning, Attention Analysis}
\label{sec:p3}
%=====================================================================

Instead of an existing benchmark, I built my own reasoning dataset per language, so I could control the correct answer. The task is simple comparisons: given two or three people or things and a property (age, height, price, quantity), say which is biggest or smallest. Each question has four possible phrasings; three are used for training and one is held out entirely, to test unseen wording. This gives 2,400 training examples and 320 test examples in each of three categories: seen names and wording, unseen names, and unseen wording, with no overlap between training and test names. Keeping these separate lets the three accuracy numbers in Table~\ref{tab:reasoning-acc} fail independently instead of blending into one number.

Each model is finetuned from its own pretrained checkpoint, tokenizer and vocabulary unchanged. Training only grades the answer part of each example, though the model still reads the full question. This is full finetuning (every weight updated) rather than a lighter memory-saving method, unnecessary at this model's small size. Both languages use identical settings, so any later difference comes from data and language, not training choices.

This setup is the result of fixing a real mistake. An earlier version, with only 24 names and 6 epochs, scored well on seen names but exactly \textbf{0.000} on both unseen tests, a classic memorization sign: with names repeated so often, the model learned to guess a familiar one instead of comparing. The fix: many more names (80 instead of 24) and fewer epochs at a lower learning rate. Every number below is from this corrected run.

The most surprising result in the whole project: Model L (Nepali) handles both unseen tests \emph{better} than Model H, despite trailing Hindi on every raw data metric in Phases 1--2. Re-running the evaluation gave the exact same numbers, so this is real, not noise. My best explanation is that this reflects what each model already understood before finetuning started, not that Nepali's language modeling is stronger; Phase 2 showed the opposite on perplexity, and the two were close to tied on the fairer byte-based measure.

These reasoning gains are not free: both models get noticeably worse at general language modeling on the original Phase 2 validation text, expected after a few epochs on a small, repetitive task. Nepali sometimes makes the same mistake, but other times gives a small typo-like distortion of the correct name instead, suggesting it was trying to recall the answer and got it slightly wrong, rather than ignoring the question. To see how finetuning changes the model internally, the same attention-analysis tool ran on the pretrained and finetuned versions, using the same comparison-question both times, so any difference is due to finetuning alone. Before finetuning, deeper layers spread attention loosely across the sentence, often anchored on the first word, a pattern also seen in Phase 2. After finetuning, in both languages without being told to, attention becomes more focused on specific, relevant words (a "spread" score drops from about 1.59 to 1.56 for Hindi, roughly flat for Nepali) and shifts slightly further back, from about 4.9 tokens to 5.0--5.1. This fits a plausible story: the model learns to actively search for and lock onto the two things being compared.

\section{Final Comparison: the Four Required Questions}
\label{sec:final-comparison}
%=====================================================================

\textbf{1. How did data scale and quality differ between Model H and Model L?} Amount of data was not the real difference: Hindi had 648.0M training tokens, Nepali 659.5M, so if anything Nepali had slightly more. The real difference is grammar: Nepali sticks endings onto words, creating far more unique word forms (6.80M vs.\ 3.96M) from a similar-sized corpus, which is also why its tokenizer needs 10.4\% more tokens per word.

\textbf{2. How do language-modeling and reasoning results compare across the two resource tiers?} On perplexity, Nepali looks 58.4\% worse; on the fairer byte-based measure, it is actually 3.4\% \emph{better}. On reasoning, the first test that measures real learned skill rather than pattern-fitting, Nepali also comes out ahead on both unseen categories. Across every metric (Table~\ref{tab:crossphase}), only token-based perplexity clearly favors Hindi; scale metrics are tied, and the byte-based measure plus all reasoning results favor Nepali.

\textbf{3. What tokenizer/corpus factors most affected the lower-resource model?} Nepali's higher token-per-word count explains the perplexity-vs-byte flip above, but not a separate gap on the harder three-way comparison task. One guess, that a specific Nepali grammatical word tokenizes inconsistently, was tested and ruled out. That gap is reported honestly as open rather than forced into an explanation that does not hold up.

\textbf{4. What evidence explains the observed differences?} The most convincing evidence came from reading individual wrong answers. Hindi mostly repeats a familiar training-data name (77--85\% of mistakes), pointing to memorization. Nepali leans more toward naming the \emph{other} real thing in the question (25--45\%), still engaging with the question even when wrong. A second, independent signal agrees: after finetuning, both models' attention shifts to focus more precisely on relevant words, direct evidence the internal processing changed, not just the outputs.

\section{Where Automation Substitutes for Human Judgment}
%=====================================================================
Places where automatic rules stood in for a human reading the text, a real limitation worth stating directly:

\begin{itemize}
\item No one read a sample of kept or rejected text by hand (Phase 1); filter settings are standard choices, not tuned by inspection.
\item Generation quality (Phase 2) is judged entirely by metrics; example sentences prove the output is on-topic, not a substitute for native-speaker judgment.
\item Attention-head labels (Phases 2--3) come from a simple statistical split, not a head-by-head check of whether each label is meaningful.
\item A fluent speaker reviewed the reasoning questions (Phase 3) for naturalness, but only the 12 underlying patterns, not all $\sim$6,000 examples; this caught one real Nepali grammar bug, fixed before the results above.
\item The extra accuracy gap on the harder three-way task: one guess was tested and ruled out, no confirmed explanation found, reported as open rather than papered over.
\end{itemize}
